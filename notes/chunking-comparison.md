# Chunking strategy comparison

Generated by `scripts/chunk_comparison.py`; do not edit by hand. The brief requires the project to compare at least two chunking strategies and report their impact on retrieval quality (item 1, `notes/report-factcheck.md` §2 row 11). Each pair below is **the same retrieval mode and the same contextualisation with only `chunk.strategy` differing**, on the same 60-item Golden QA Set, so the difference is attributable to chunking. A pair that differs in a second factor is refused, not averaged.

`fixed` splits on character windows with a 64-word overlap; `recursive_parent_child` splits on structural units (headings, sentences, table rows, code fences) and keeps the coarser parent for the generator. Its hypothesis is that keeping tables and code fences atomic is worth the token budget it costs.

## Does the atomic-table hypothesis survive here?

The largest movement in hit@10 across the 8 finished pair(s) is +0.0500 in `dense` / `contextual_prefix` (paired McNemar p = 0.5000). Atomicity itself did happen: 87% of the recursive chunks that exceed the budget carry a table row or a code fence, so the splitter kept them whole at the cost of the token budget, and the share of chunks ending mid-sentence falls from 0.5745 to 0.1865. The one thing chunk strategy does move is how often an answer carries a supported citation: 1 of 8 pairs shift significantly, the largest being +7 items in `dense/contextual_prefix` (p = 0.0156), and the sign is not the same in every pair — so the mechanism buys citation coverage rather than retrieval quality. The `table_content` items — the golden questions whose answer sits in a table — do not move significantly in any pair, so keeping tables atomic did not measurably help the questions it was meant to help. On this corpus the atomic-table hypothesis does not survive: chunk strategy changes how chunks are built and how often an answer is cited, not how well retrieval works.
